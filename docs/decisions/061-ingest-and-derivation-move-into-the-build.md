# 061 — Ingest and the occurrence derivation move into the build: derivation first, one source at a time, each checked against Postgres until it agrees

**Status:** accepted · **Decided:** 2026-09-30 · **Answers:** the design of `salish-xv35` (decision [056](056-the-logged-out-read-path-is-built-as-static-files.md) step 3) · **Extends:** [059](059-the-end-state-is-a-build-graph-with-a-small-authoritative-store.md) · **Amends:** [011](011-ingest-imperative-shell.md) (where the shell runs and what it persists to), [055](055-occurrences-are-stored-not-assembled.md) (the derivation leaves SQL-in-Postgres), [008](008-source-schemas-are-upstream-mirrors.md) (the mirrors leave Postgres, and lose their two resolved columns)

## Context

Decision 056 said step 3 in one sentence: the ingest's pure transforms write snapshots instead of Postgres rows, and the five views behind `derived.occurrences` are ported to DuckDB and checked row for row against the stored table until they agree. Decision 059 made it the prerequisite for the end state. This record is the design, written after reading what is actually there.

Three things the one sentence did not say.

**A signed-in contributor reads Postgres live.** `src/salish-sea.ts` and `src/date-calendar.ts` take the static path only when no user is signed in; a contributor's map and calendar come from PostgREST. If pg_cron stopped feeding `derived.occurrences`, a signed-in user would lose every upstream sighting until step 4 moved their reads too.

**Happywhale has no ingest to move.** Its only loader is HTTP code inside Postgres that migration `20260731120000` retired; there is no cron job and `ingest.runs` has never held a Happywhale row. `happywhale.*` is a frozen table.

**The mirrors can be fetched again, but not by a build.** Maplify serves history (a June 2024 window returns 221 rows), iNaturalist's was backfilled once already ([041](041-inaturalist-history-backfilled.md)), and Orcasound is read whole on every run. So 059's premise holds. But a run fetches ten days, so a destroyed mirror plus a build gives ten days of data; getting the rest back is a rate-limited backfill job, not a rebuild.

## Decision

**The derivation is ported first, over Postgres's own raw tables, and the ingest moves second.** The hardest question the epic left open was what "agree" means for rows whose derivation depends on reference data at a moment in time. That question exists only if the two sides fetch independently. The snapshot already reads everything in one transaction ([`scripts/read-path/snapshot.ts`](../../scripts/read-path/snapshot.ts)); widened to the raw source tables and the reference tables the views join, it hands the DuckDB port and the stored table identical inputs, and the diff is exact. The ingest can then move one source at a time behind a derivation already known to be right.

**The port writes the same document Postgres does.** The five views become DuckDB SQL under `scripts/read-path/`, run by a node script, and their output is a `doc` column in the shape `to_jsonb(occurrence)` produces today. The day files, the calendar, the id index and the profile pages read `snapshot.occurrences` and never learn that its producer changed. Agreement is checked on parsed documents, not bytes: Postgres and DuckDB do not render `48.50566` or a timestamp identically, so the files change bytes exactly once, at cutover, and mean the same thing.

**Agreement is a gate in the build, not a script someone runs.** A rule node compares the ported relation against the stored one and fails the build on any difference, naming the rows. It runs on every build for as long as both exist. When it has been green long enough, the downstream tasks' inputs move to the ported relation and the gate is retired. Each source's ingest gets the same treatment later: its local mirror against that source's Postgres table, while both ingests run.

**Each source's mirror is a SQLite file, holding only what upstream said.** One per source (Maplify; iNaturalist, with its taxa; Orcasound), rows keyed by the source's id and stored as the normalized record the pure core already produces. Two columns Postgres's mirrors carry today are dropped: `maplify.sightings.entity_id` and `collection_id` are resolved at ingest time now, by the register's name index and `maplify.resolve_collection`. That resolution moves into the derivation, so a mirror is exactly a mirror (decision 008, applied more strictly than before), and a new register edition reruns the derivation because its input changed, instead of re-ingesting. Nobody edits those columns by hand, so nothing is lost.

Why SQLite rather than DuckDB tables: `node:sqlite` is built into the node the scripts already run on; Litestream replicates it; and step 4's write API is a resident process that holds the native store open for writes while builds read it, which DuckDB permits only within one process. The mirrors alone would work either way. Making them the same shape as the store step 4 adds means the end state has one kind of store, read one way. Stelis already content-addresses a SQLite store key by key for BeeAtlas's notes ([`notes-digest.rkt`](https://github.com/rainhead/stelis/blob/2f98ced4756fbfaed84eabfd49483c7a29380a99/src/notes-digest.rkt)).

The mirrors are derived, not authoritative: a lost one is rebuilt by running the ingest over past windows, which the 011 shell already accepts as a curator's `start`/`end`. That takes hours against iNaturalist's limits, so replicating them off the machine is worth its cost, but it is a convenience. Only what our users write can never be regenerated (059).

**The ingest's shell moves to the build machine; its core stays where it is.** The pure transforms in [`scripts/ingest/`](../../scripts/ingest/) are shared today between the Deno function and vitest, and stay. What moves is the fetch loop in `supabase/functions/ingest/fetch-*.ts` and the persist step: a node script per source, run by Stelis as a boundary task, fetching the ten-day window (or the whole corpus, for Orcasound), reconciling it against the mirror with the same `{upsert, delete}` the core computes now, and writing the mirror. The completeness rule of 011 is unchanged: a fetch that is not provably complete writes nothing. A run that changed nothing reports so through Stelis's boundary receipt, so the build can say "Maplify: unchanged, 0 records since …" rather than only "outputs identical". Order of migration: Orcasound (stateless, no window), then Maplify (window and reconcile), then iNaturalist (window, taxa closure, photos).

**A signed-in contributor reads the files too, before the Postgres ingest stops.** The overlay: a signed-in tab reads the day files for everything upstream and asks PostgREST only for the native sightings, merging by id with the live row winning. The calendar adds live native counts to the file's. A `?o=` link to a sighting younger than a build keeps its Supabase lookup, which signed-in tabs already have. This is step 4's read path arriving one step early, not a temporary arrangement, and it is what lets pg_cron's ingest be unscheduled at this step's cutover rather than run doubled until step 4. It changes what a contributor sees in one way: upstream sightings arrive within one build instead of within one ingest tick.

**So the build's cadence becomes the ingest's, and is measured before the cutover.** Ingest runs every five minutes today. Stelis's first slice (its `st-ml9`) owes the measurements a five-minute build needs: what a build that finds nothing costs on the Fly machine, and how its history grows at 288 builds a day. Those are taken before the overlay cutover, not after.

**What stays in Postgres for this step.** Native sightings and their photos, the catalogue (`individuals`, `social_groups`, `designations` and their kin), the register as `scripts/register/load.ts` loads it, contributors, and the provider reference tables. The build snapshots them as it does today. Moving the register load into the build is real work with its own record; it is not what step 3 is for.

## Rejected alternatives

- **Move the ingest first.** It is the half the epic is named for. But every comparison would then be between two independently fetched corpora, and every difference would need to be explained as either a bug or a timing artefact. Porting the derivation first over one snapshot makes the first comparison exact and the later ones (mirror against mirror) simple.
- **Keep pg_cron's ingest running alongside the build's until step 4.** No frontend work, and no cadence prerequisite. But every source is fetched twice, iNaturalist's limits ([041](041-inaturalist-history-backfilled.md)) are the pinch, and "Postgres holds only what users write" would not be true until step 4.
- **Write each fetched window as an immutable file and derive the mirror as a fold over all of them.** Every row's provenance would be the fetch that last saw it. But at 288 runs a day the files outgrow the volume within months, and compacting them is the mirror again with an audit log beside it. The audit log is `ingest.runs`, kept.
- **DuckDB tables for the mirrors.** Argued above; it works for the mirrors and not for the store step 4 adds.
- **Port the derivation into Stelis's own derivation nodes.** Stelis's ADR 0008 reserves those for unbounded-depth closure with a native "why"; five joins over sixty thousand rows is DuckDB's job.

## Consequences

- The `read_path` role is granted the raw source tables and the reference tables the views join, and [`read-path-grants.test.ts`](../../supabase/read-path-grants.test.ts) pins the new list. `public.contributors` gets a column list, as `individuals` has, so email addresses never reach the build machine.
- Porting hazards known in advance: Postgres's `\m` and `\M` word boundaries and the lookbehind in `register.fold` (DuckDB's RE2 has neither); the ancestor-and-deprecation union in `register.inaturalist_taxon`; `inaturalist.species_id` comparing ranks by enum order; `DISTINCT ON`; Happywhale's per-row `AT TIME ZONE`, which DuckDB's ICU does but whose daylight-saving rows are the ones to test.
- Peak memory of the derivation and of each ingest script is measured before it is deployed; the Fly machine is 1 GB with no swap and has been taken down by a build task twice.
- The heartbeat ([012](012-ingest-heartbeat.md), [060](060-an-upstream-outage-is-held-to-a-longer-threshold.md)) reads `ingest.runs`. Once a source's ingest runs in the build, its runs are recorded by Stelis's build history and the operator build log, and the heartbeat's questions ("is our side running", "is the source reachable") are asked of that instead. Each source keeps writing `ingest.runs` until its Postgres ingest is unscheduled, so the heartbeat never goes blind mid-migration.
- On Stelis's side: a keyed SQLite store as a task's output rather than only a leaf (the notes store is read-only from the graph's point of view), and a rule node that says two relations must agree, reusable for each source's gate. Both are small; neither is delta propagation or a Racket derivation.
- The `ingest` Deno function, its trigger secret and the three pg_cron jobs are retired one source at a time, each in the migration that unschedules it, once that source's gate has been green and the overlay is live.
